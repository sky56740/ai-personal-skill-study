concept-explainer

Skill 可复用指令包

把"在某个场景下如何做一件事"沉淀成可被 Agent 自动调用的标准化文本。

我的理解：Skill相当于给Agent一份标准化工作手册。把固定步骤、输出格式、检查要求写进文件。遇到同类任务Agent直接读取手册，不用每一次重新思考怎么干活。Skill不等同一小段提示词，是完整、可以反复使用的项目文件。

1. 一句话定义

Skill = 一份带有 YAML 元数据 + Markdown 正文 + 可选资源的目录， 告诉 Agent 在何时、如何调用什么样的工作流，让"知道怎么做"这件事从对话里被搬到仓库里沉淀。

Skill 不是插件、不是工具，而是一种知识与流程的封装格式。

2. 核心机制 / 组成

一个典型的 Skill 目录长这样：

.workbuddy/skills/<skill-name>/
├── SKILL.md          # YAML frontmatter + 工作流正文
├── scripts/          # 可选：可执行脚本
├── references/       # 可选：被正文引用的资料
└── assets/           # 可选：模板、图标等静态资源
  • YAML frontmatter：name + description + 触发条件——决定 Skill 能否被"自动"识别。
  • 适用场景：什么时候用，什么时候不要用。
  • 输入信息：调用时要给什么字段，缺字段时怎么办。
  • 生成步骤：按顺序执行的工序清单。
  • 输出结构：固定模板，避免每次返工。
  • 自检要求：跑完怎么知道没出问题。

3. 一个具体应用场景

任务：用本仓库里的 concept-explainer Skill 学习新概念。

  1. 输入：用户说"用 concept-explainer 学习 RAG"。
  2. Skill 加载：WorkBuddy 发现 .workbuddy/skills/concept-explainer/SKILL.md，把 YAML 元数据纳入索引。
  3. 上下文注入：匹配到任务后，把 SKILL.md 的正文作为 system prompt 的一部分塞进上下文。
  4. 流程驱动：Agent 按 SKILL.md 第 3 节列出的 10 步工序执行。
  5. 输出：learning-materials/rag.html。
  6. 自检：按 §6 自检清单跑一遍；不通过就回头补。

4. 容易混淆的问题与使用边界

Skill ≠ System Prompt

System prompt 是当下会话的"上下文"；Skill 是被加载进上下文的"模板"。

Skill ≠ Tool

Tool 是 Agent 能调用的外部能力；Skill 是给 Agent 看的指令。

Skill ≠ Workflow

Workflow 强调"编排"，跨多个 Agent / 工具；Skill 强调"知识沉淀"，给单 Agent 用。

Skill ≠ Plugin

Plugin 多指外部服务/连接器；Skill 是纯本地 Markdown，无网络依赖。

  • 作用域：用户级 Skill（~/.workbuddy/skills/）在所有项目生效；项目级 Skill（仓库内 .workbuddy/skills/）只对当前仓库生效。
  • 使用边界：description 写不准的 Skill，永远不会被自动触发。
  • 设计边界：Skill 不应承担"长流程编排"——那是 Workflow 的活；Skill 也不应改模型权重——那是 Fine-tuning。

5. 自测问题

Q1. Skill 的 description 字段为什么重要？

它是 Skill 被"自动识别"的关键：写得太宽会被乱触发，写得太窄永远不会触发。

Q2. 项目级 Skill 和用户级 Skill 的区别？

项目级只对当前仓库生效、可随仓库共享；用户级在所有项目都生效、只在本机。

Q3. Skill 能不能包含 Python 脚本？

可以放在 scripts/，但要明确用途；不要让脚本副作用过大，否则每次触发都跑一遍。

Q4. 一个 Skill 写多大合适？

正文建议控制在 200~600 行；过长会让上下文被 Skill 自身占满，反而挤压任务内容。

Q5. Skill 适合做"对比两个概念"吗？

勉强可以，但更适合另起一个 concept-vs Skill，避免把 comparison 写进通用 explainer。
