Agent 上下文 Skill

三个概念的关系图

Agent 在上下文中读到 Skill，按 Skill 流程调用工具、产出结果。

三者之间的关系：
  1. 上下文是记忆基础。没有足够的上下文窗口，Agent读取不到Skill规则，记不住任务，就无法正常运行。
  2. Agent属于执行者。依靠大模型推理，上下文保存信息，读取Skill中的流程，完成复杂任务。
  3. Skill负责沉淀复用逻辑。将经常使用的流程固化下来，减少重复推理，输出结果更稳定。

3. 重点 ①：上下文如何影响 Agent 的工作

上下文的"信息密度"决定 Agent 的判断质量。 把 RAG 检索结果、Skill 正文、历史对话、工具返回值都拼装得当，Agent 才能做出符合预期的决策。
上下文是 Agent 唯一的"记忆"。 LLM 没有持久记忆——想让 Agent 知道某件事，要么写进上下文，要么让它主动去查（工具 / RAG）。
上下文是"容量受限"的工作台。 窗口有上限；超出后旧内容会被截断；研究中段信息最易丢失（Lost in the Middle）。
上下文决定"能做什么"，但不决定"该不该做"。 权限、安全、合规这些是另一层（人 / 平台规则）。

4. 重点 ②：Skill 如何沉淀可复用的任务知识

Skill 把"经验"从对话搬到仓库。 一段好用的提示词本来只在某个对话里用过一次；写成 Skill.md 后，下一个会话、下一台机器都能复用。
Skill 是"被加载的模板"，不是"被调用的工具"。 它通过 YAML 元数据被匹配，匹配后注入上下文，再由 Agent 按里面的流程执行。
Skill 让"经验可版本管理"。 可以和仓库一起 git commit、code review、diff——比"我把这段 prompt 截图发群里"靠谱得多。
Skill 的边界 = 它不该做"长流程编排"。 跨多个 Agent、跨多小时的任务更适合 Workflow；Skill 适合"在 200~600 行里说清楚一次怎么干"。

5. 一个具体例子把三者串起来

假设我说："用 concept-explainer 学习 RAG"，背后发生了什么：

  1. Skill 发现：WorkBuddy 扫描 .workbuddy/skills/，发现 concept-explainer/SKILL.md。
  2. Skill 匹配：YAML 中 description 含"概念学习"，命中任务。
  3. Skill 注入上下文：把 SKILL.md 正文追加到 system prompt。
  4. Agent 推理：LLM 看到任务 + Skill 流程，决定要写 HTML。
  5. Agent 调用工具：写入 learning-materials/rag.html。
  6. 自检：按 Skill §6 自检清单逐条跑；不通过就回到步骤 4。
  7. 交付：呈现给用户。

这整个链路里：Skill 是流程的"标准答案"， 上下文 是"标准答案 + 当前任务"的合并视图， Agent 是"按这份合并视图动手干活的工人"。

6. 我自己的判断（写给自己看的备忘）

  • 很多人把"Skill"和"Agent"混着叫。其实 Skill 是被加载的，Agent 是干活的——这个先后关系不能倒。
  • "上下文工程"（Context Engineering）这个词比"Prompt 工程"更准确——因为提示词只是上下文的一部分。
  • Skill 写得好 ≠ Skill 写得多。控制 200~600 行、把自检写死，比堆一千行更靠谱。
  • 如果某个任务连"用哪份 Skill 都说不清"，那是 Skill 体系没设计好，不是用户没用对。
