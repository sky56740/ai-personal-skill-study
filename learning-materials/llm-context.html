大模型的上下文 Context

LLM 生成下一个 token 时，模型"眼前"所能看到的所有文字总和。

我的理解：上下文就是大模型短期的记忆力。模型只能记住窗口范围之内的文字。一旦内容超出窗口，更早的信息它就看不见，直接忘掉。Agent能否正常干活，很大程度受上下文窗口的限制。

1. 一句话定义

上下文（Context）是模型一次推理所能"看到"的全部输入文本，由系统提示、用户消息、历史对话、工具结果等拼装而成。

它临时存在、随会话变化；模型不会"记住"它，除非你显式写回。

2. 核心机制 / 组成

  1. System Prompt

    角色与规则设定。一般优先级最高，决定模型的"人设"。

  2. User Prompt

    用户当前输入的问题或指令。

  3. 对话历史

    之前若干轮问答，自动续到上下文里。窗口越大，历史可保留越长。

  4. 工具结果

    Function Calling / 搜索 / RAG 返回的内容，由模型主动拉进来。

  5. 长上下文（Long Context）

    现代 LLM 上下文窗口可达 128K ~ 数百万 token；不是越大越好，后面会说。

  6. 上下文窗口 Context Window

    模型一次性能处理的最大 token 数；超出后旧内容会被截断或压缩。

3. 一个具体应用场景

任务：让模型基于一篇 30 页 PDF 回答细节问题。

  1. 输入：用户上传 PDF + "第 17 页第 3 段的结论是什么？"。
  2. 上下文组装：系统提示（你是文档助手） + 历史对话 + PDF 全文（被切分、嵌入 user prompt）。
  3. 模型推理：从上下文里定位段落 → 生成答案。
  4. 输出：引用第 17 页的结论。

这就是 RAG 的简化原型——RAG 本质是把外部信息临时塞进上下文，而不是改模型参数。

4. 容易混淆的问题与使用边界

上下文 ≠ 上下文窗口

上下文是"内容"，窗口是"容量上限"；100K 窗口可以只放 200 token 内容。

长上下文 ≠ 完美记忆

研究表明模型对中段内容的注意力最弱（"Lost in the Middle"）。

上下文 ≠ 训练数据

上下文是当次输入；训练数据是模型权重，离线学到。

System ≠ User Prompt

System prompt 设定"人设"与规则，权重通常高于 user prompt。

  • 使用边界：上下文越长，单次成本越高、延迟越长，还可能稀释关键信息。
  • 隐私边界：塞进上下文的内容可能被日志/缓存记录，不传敏感信息。
  • 版本边界：上下文窗口大小随模型版本变化，老问题用新模型答案不一定一致。

5. 自测问题

Q1. "上下文"和"上下文窗口"是一回事吗？

不是。窗口是容量上限，上下文是当前塞进去的内容。

Q2. 长上下文模型能"完美读完"一本书吗？

不能。位置偏差（Lost in the Middle）使中段信息被忽略；仍需要 RAG / 摘要辅助。

Q3. RAG 和"把文档塞进上下文"是什么关系？

RAG 是"按需检索相关片段塞进上下文"的工程化做法，不是替代上下文。

Q4. 为什么不能把密码 / API Key 直接写进 system prompt？

上下文可能被记录、日志、缓存复盘，是高风险暴露面。

Q5. 上下文变长后会发生什么副作用？

成本上升、延迟变长、关键信息被淹没、还可能触发截断或注意力下降。
